# AR Character Hunt (ari-game-v1)

A mobile web AR game. Open the link on your phone, point the **back camera**
around, and find characters floating inside glowing **spheres** scattered every
**10–20 feet** in real physical space — **indoors or outdoors**. Tap (or walk
into) a sphere to catch the character.

Fully **self-contained**: upload your cast of **151–200 characters** right in
the app (no accounts, no backend). Everything runs as a static site.

## How it works

### Indoor + outdoor AR
Placement is **metric**, so it isn't tied to GPS:

- **WebXR (`immersive-ar`)** — on devices that support it (Android Chrome with
  ARCore, AR headsets) you get full positional tracking: spheres are anchored
  in the room and you **physically walk** between them, 10–20 ft apart, inside
  or outside.
- **Look-around fallback** — on devices without WebXR AR (e.g. iOS Safari) the
  app uses the live camera feed + gyroscope so you can pan around to find and
  tap spheres arranged on a viewable dome.

### Characters: upload in the app
Open **admin.html**, tap **Upload character images**, and select your images
(PNG/JPG/SVG/WebP). Each image becomes a character (the filename becomes its
name). They're stored on the device via **IndexedDB** — no server needed. Until
you upload your own, a 12-character seed cast ships with the site.

- **Frequency** — per-character relative spawn weight (0 disables, higher = more
  common).
- **Sphere style** — set a default look (radius, color, opacity, metalness,
  roughness, character scale, wireframe, float) and override it per character.
- **Spawn behavior** — count, min/max spacing (feet), spread radius.
- **Export / Import pack** — move your characters + settings between devices as
  a single JSON file.

> Storage is per-device/per-browser. Set up your cast on the device you'll play
> on, or use Export/Import to copy a pack across devices.

## Run locally

```bash
npm install
npm run seed     # generates the bundled seed roster + default-config.json
npm start        # http://localhost:3000  (game)   /admin.html (setup)
```

Camera/AR need a **secure context**. `localhost` is treated as secure for the
camera; for full WebXR on a phone, use the deployed HTTPS link or an HTTPS
tunnel (e.g. `ngrok http 3000`).

## Optional: seed the default roster from Google Drive

If you'd rather bake a default cast into the site from a Drive folder (instead
of, or in addition to, in-app uploads): set `DRIVE_FOLDER_ID` +
`GOOGLE_SERVICE_ACCOUNT_JSON` (see `.env.example`), run `npm run sync`, and
commit. There's a manual `drive-sync` workflow for the same in CI. In-app
uploads always take precedence over the baked-in default on a given device.

## Adding AriMon cards (no code edits)

Card art lives in `public/assets/cards/` and the game reads
`public/data/cards.json` as the source of truth. To register new cards:

1. Drop the PNG(s) into `public/assets/cards/`. Either naming style works:
   - `001-turtwig-ari.png`  → id `001`, name "Turtwig Ari"
   - `007_SquirtAri.png`    → id `007`, name "SquirtAri"
   (the first three digits become the id and the `###/151` number).
2. Regenerate the manifest:
   ```bash
   npm run build:cards
   ```
3. (Optional) Curate `name`, `type`, `rarity` in `public/data/cards.json` —
   those manual values are preserved across re-runs. Add `"lockName": true`
   to keep a hand-tuned name even if the file is later renamed.

`npm run check:cards` verifies the manifest matches the files (handy in CI).

## Real-life Stuffies (experimental)

From the start screen choose **Stuffies · Create & scan**. A parent registers a
toy with 2–4 centered reference photos. Use a full-body first photo on a plain
contrasting background; adjust edge-based background removal, or keep the
original. The browser renders a full-body PNG and a collectible card. No AI
image generation or 3D mesh is used.

In the unified camera hunt, tap the actual toy to claim it after matching. MobileNet
image embeddings are compared locally against the references. The matcher is experimental and can confuse similar
toys or photos of toys; it is not a verified object detector or liveness check.
There is no random spawn for Stuffies. The existing AriMon
cards and collection keys are unchanged; the Binder has a separate Stuffies
section. The scan screen works with the regular phone camera, not immersive
WebXR camera pixels.

The model is downloaded from public TensorFlow.js/MobileNet hosts on first
use (internet required); reference features, rendered images, and claims live
in separate local IndexedDB on the playing browser. Photos are not sent to a
server or committed to the public repo. No cross-device sync or backup yet.
Browser data removal can erase the local collection.

### Unified camera hunt update

Start hunting now uses one camera view for both Ari Balls and real Stuffies. Tap a ball or tap the real toy. Multiple crop sizes and two matching checks on the tapped region replace automatic claiming. A repeated center match shows an aiming cue, not a detected bounding box. The same local registrations and binder claims are retained. Unified hunt uses look-around AR on all devices (no immersive WebXR camera access). Recognition is experimental; no physical accuracy benchmark yet.

### 3D plush preview

The first procedural model is Turtwig (registered names containing Turtwig or Turtle Wig). On a successful catch or when opened in the Stuffies binder, the actual 3D mesh can rotate by touch, with a toggle back to the original collectible card. The geometry is an approximation of the plush, not a photogrammetric reconstruction. Other registered toys continue to display their original card. No reference-photo or storage migration; the 3D asset does not change recognition.

The 3D roster now includes Pikachu and Charmander, with sculpted plush proportions, facial stitching, back markings and tails based on supplied photos. Register each on the playing device under its name (2–4 real photos). The model activates after camera claim or in the binder. No personal photos are bundled in the public repository.

### Recognition field-test adjustment

A match no longer requires two different reference angles to score highly at once. Tap claims require two agreeing frames, with a minimum score and competing-toy margin, and stronger combined evidence. New registrations use three crop scales per reference. In Stuffies setup, **Teach views** appends reference embeddings to an existing toy without changing its ID, card, or claim state. Use real photos from the current room and different angles. Matching thresholds are heuristic; physical accuracy is not yet validated.
